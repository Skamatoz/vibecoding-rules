# Правила разработки

Правила для ИИ-ассистента (Claude Code, Codex, Cursor), который пишет код в этом проекте. Собраны из живых проектов: CRM с платежами и выплатами, чат-платформы для продаж, сайта с админкой. Почти каждое правило — ответ на то, что однажды уже сломалось.

Если правило противоречит CLAUDE.md проекта, прав CLAUDE.md. Если правило мешает задаче, скажи об этом владельцу, а не обходи молча.

Защита сервера и проверки перед запуском — `docs/server.md`, читать по необходимости.

---

## 0. Как работать

- Перед тем как писать код, прочитай CLAUDE.md и README.md нужного сервиса. Ответа там нет — читай код, а не придумывай.
- Не знаешь, как устроен внешний API (поля, коды ответа, подпись), — сверься с живой документацией или спроси. Выдуманное поле хуже вопроса.
- Делай то, о чём просили. Легаси «по дороге» не чини, чужое не переименовывай и не переформатируй: попутные правки раздувают дифф и ломают несвязанное. Увидел проблему — напиши о ней.
- Перед коммитом — `pnpm build` (а если есть, `pnpm check`) без ошибок. Не собирается — не коммить.
- Коммить только свои файлы: в репозитории могут работать параллельные сессии. Перед коммитом — `git status` и `git diff`.
- Необратимое и внешнее делай только по прямому слову владельца: публикацию, рассылку, платёж, удаление данных, DNS, настройки сервера и панели деплоя, перевыпуск ключей.
- Цифры и факты — только из источников. Не проверил — так и скажи.
- Поменял поведение — поправь CLAUDE.md и README в том же коммите. Устаревшая документация вреднее отсутствующей: ассистент ей верит и ломает рабочее.
- Владелец от чего-то отказался — запиши в CLAUDE.md: «Отказались: … (дата)». Иначе следующая сессия предложит это снова.
- Комментарий в коде объясняет ЗАЧЕМ. У опасного места пиши, что здесь НЕЛЬЗЯ и почему, с датой случая. Иначе следующая сессия «оптимизирует» обратно.
- Большую переделку начинай с плана в файле: что меняем, точный список файлов, шаги, как проверить, как откатить.
- Хук или гвард заблокировал команду — не обходи его: другой флаг, скрипт-обёртка, подмена env. Скажи владельцу, что хотел сделать и зачем.

## 1. Масштаб: маленький продукт, а не корпорация

По привычке ты проектируешь так, будто у продукта миллионы пользователей и сто разработчиков. Здесь это не так. Масштаб проекта записан в CLAUDE.md, в разделе «Масштаб». Если его нет — спроси, прежде чем проектировать.

Если не сказано другое, проект такой:
- продукт для малого бизнеса или своей команды: CRM, ERP, учёт, склад, запись, кабинет клиента, бот, сайт с админкой;
- от единиц до нескольких тысяч пользователей, обычно меньше десятка запросов в секунду;
- база до десятков миллионов строк;
- один-два разработчика с ИИ-ассистентом;
- один VPS с Dokploy.

Что из этого следует:
- Один сервер с Postgres держит такой продукт с большим запасом. Если тормозит — почти всегда виноват запрос без индекса или выборка лишних полей, а не «нужен кластер».
- Сложность добавляется под измеренную проблему (лог, метрика, медленный запрос), а не «на вырост». «Потом будет нагрузка» — не причина.
- Код читается за вечер. Слои «на будущее» не нужны: интерфейс с одной реализацией, репозиторий поверх Prisma, DI-контейнер, фабрики, классы use-case, «порты и адаптеры». Функция в `services/`, в ней вызов Prisma (раздел 4).
- Предлагаешь решение — скажи, сколько оно добавляет: новых сервисов, зависимостей, мест, где может сломаться ночью.

Без измеренной причины и без согласия владельца не предлагай:

| Хочется | Вместо этого | Когда это оправдано |
|---|---|---|
| Kubernetes, Helm, Terraform, свой CI для выкладки | Dokploy: пуш в `main`, он сам собирает и выкладывает (раздел 11) | несколько серверов и человек, который их ведёт |
| Микросервисы | один API с модулями (раздел 3) | только другое место запуска или сеть (раздел 3) |
| Kafka, RabbitMQ, BullMQ | таблица-очередь в Postgres (раздел 9) | сотни заданий в секунду постоянно |
| Redis для кэша и сессий | индекс, `select` только нужных полей, кэш в памяти процесса | замерено, что база не справляется, хотя индексы есть |
| Elasticsearch | полнотекстовый поиск Postgres, `pg_trgm` | миллионы документов и релевантность, которой нет в Postgres |
| GraphQL, tRPC | REST-маршруты Hono + Zod | не для этого масштаба |
| Keycloak, Auth0, отдельный сервис входа | вход в самом API (раздел 6) | общий вход для нескольких продуктов |
| MongoDB рядом с Postgres | колонка `jsonb` в Postgres | не для этого масштаба |
| Event sourcing, CQRS, саги | статус в колонке и журнал изменений | не для этого масштаба |
| Serverless, облачные функции | обычный процесс в контейнере | не для этого масштаба |
| Реплики, шардинг | один Postgres и ежедневный бэкап | база не тянет после индексов и разбора медленных запросов |
| Nx, Turborepo, общий пакет `shared` | папки в одном репозитории | не для этого масштаба |

Не путай масштаб инфраструктуры с качеством. Маленький продукт — это меньше серверов и слоёв, а не упрощённая безопасность. Права, вход, деньги, миграции, бэкапы и обработку ошибок делай по-взрослому при любом размере: утечка клиентской базы из CRM на восемь человек — такая же утечка.

## 2. Стек по умолчанию

Один язык везде — TypeScript. Каждая часть — популярная и скучная: ИИ знает её хорошо и не выдумывает.

- **Бэкенд:** Node 22, TypeScript в режиме `strict` (ESM), Hono 4 + `@hono/node-server`, Zod + `@hono/zod-validator`, Prisma 6 + PostgreSQL 17. Пароли — `bcryptjs`, сессии — `jsonwebtoken`, прокси и таймауты — `undici`, картинки — `sharp`, файлы — S3-совместимое хранилище.
- **Фронт:** Nuxt 4 (код в `app/`), Vue 3, Nuxt UI 4 + Tailwind 4, иконки lucide в бандле. Публичный сайт — SSR, админка и кабинет — SPA (раздел 3).
- **Пакеты:** pnpm, lockfile в git, в Docker — `pnpm install --frozen-lockfile`.
- **Деплой:** Docker и Dokploy на своём VPS, автодеплой на пуш в `main` (раздел 11).
- **Telegram-боты:** grammy.
- **Очереди и расписания:** таблицы в Postgres (раздел 9).
- **Тесты:** `node:test` через tsx — на деньги, права, вебхуки и разбор внешних ответов. Покрытие ради покрытия не нужно.
- Новая зависимость — только с объяснением, зачем. Ради одной функции библиотеку не тащи.
- Версию закрепляй точно, если бинарь должен совпасть: Prisma CLI с клиентом.

## 3. Архитектура: один бэкенд, а не зоопарк

По умолчанию проект — это **один API и фронты к нему**. Части системы — модули внутри API, а не отдельные сервисы.

| Продукт | Из чего состоит |
|---|---|
| CRM, ERP, учёт, склад для своей команды | `api` + `admin` (SPA) + Postgres |
| Сайт с заявками или блогом | `site` (SSR) + `api` + `admin` (SPA) + Postgres |
| Кабинет клиента с оплатой | `api` + `app` (SPA) + Postgres, лендинг `site` (SSR) — если нужен |
| Telegram-бот с админкой | `api` + `bot` + `admin` (SPA) + Postgres |

**Сайт — SSR, всё за логином — SPA**
- Публичный сайт — это то, что ищут в поиске и чем делятся ссылкой: лендинг, блог, каталог, страницы услуг. Он делается на Nuxt с SSR и живёт на основном домене `example.ru`. SPA поисковик видит пустой страницей, а мессенджеры не собирают для неё превью ссылки.
- Админка, CRM, кабинет — всё, что за логином, — Nuxt SPA (`ssr: false`) на поддомене: `admin.example.ru`, `app.example.ru`. SEO там не нужно, а без SSR нет расхождений между сервером и браузером.
- API — на `api.example.ru`.
- Сайт и админка — разные приложения, а не одно Nuxt-приложение в двух режимах. У них разные рендер, кэш и заголовки безопасности (админку нельзя открывать во фрейме), и упавшая админка не роняет сайт.

**Когда нужен отдельный сервис**
- Отдельный сервис заводи, только если у него другое место запуска или другая сеть:
  - публичный SSR-сайт и SPA-админка — у них разные кэш, домены и требования;
  - тяжёлый рантайм со своим лимитом памяти (Chrome, ffmpeg);
  - шлюз, который должен стоять в другой стране или сети;
  - бот на long-polling: Telegram пускает к токену только один процесс.
- **Не дели сервисы по предметным областям** («платежи», «чат», «уведомления») при общей базе. Получится распределённый монолит: копия схемы в каждом сервисе, файлы-близнецы, которые расходятся, межсервисные токены ради одного SELECT, дубли уведомлений при деплое. Так уже было: чат вынесли в отдельный сервис ради WebSocket, а потом влили обратно.
- **У базы один владелец** — API, который держит схему и миграции. Другие сервисы в эту базу не ходят. Если без этого никак (сайт читает статьи напрямую ради скорости), то:
  - только чтение;
  - отдельный пользователь базы с правами только на нужные таблицы;
  - поля перечислены поимённо в CLAUDE.md владельца: «менять только вместе с сайтом».
- Если сервисов несколько, у каждой пары свой токен: утечёт один — остальные целы. Пустой токен значит «отказ всем», а не «пускать всех».

## 4. Устройство кода

Код пишут сессии ИИ одна за другой, и каждая видит только кусок. Поэтому раскладка должна быть предсказуемой: по папке сразу ясно, что в файле можно и чего нельзя.

**Размеры**
- Файл — до 300 строк, 600 — потолок: такой файл режь. Страница Nuxt — до 200 строк, функция — до 50.
- Режь по смыслу: по сущности или шагу (`deals/create.ts`, `deals/close.ts`), по куску экрана (`DealHistory.vue`). Не `part1`/`part2` и не `utils2.ts`.
- Один файл — одна ответственность, имя говорит, что внутри: `deals.service.ts`, `DealCard.vue`, `useDeals.ts`.
- Справочники (статусы, их подписи и цвета, форматы денег и дат) — сразу в одном месте. Логику обобщай на третьей копии, не раньше: неудачная общая функция хуже двух похожих.
- Раскладку и размеры сторожит скрипт `pnpm check:arch` (`scripts/check-architecture.mjs` в каждом сервисе), он входит в проверку перед коммитом. В одной системе на бэкенде со сторожем самый большой файл держался на 590 строках. На фронте сторожа не было, и компоненты доросли до 950 строк: целиком их не прочитать ни человеку, ни ИИ.

**Бэкенд (Hono)**

```
api/src/
  index.ts      запуск: env, сервер, воркеры, плавная остановка
  app.ts        сборка: middleware, маршруты, app.onError
  routes/       по файлу на раздел: deals.ts, clients.ts
  services/     по папке на раздел: deals/, clients/ — вся логика
  middleware/   вход, права, CSRF, лимиты
  workers/      фоновые задачи и их менеджер
  lib/          env, prisma, fetch с таймаутом, логгер, S3 — о домене не знает
```

- **Роут — тонкий:** схема Zod → права → вызов одного сервиса → ответ.
  ```ts
  deals.post('/', requirePermission('deals', 'create'), zValidator('json', createDealSchema), async (c) => {
    const deal = await createDeal(c.get('user'), c.req.valid('json'))
    return c.json(deal, 201)
  })
  ```
  В роуте нет запросов к базе, расчётов, циклов по данным, вызовов внешних API и отправки уведомлений. Роут длиннее 15 строк — значит, логика утекла в него.
- **Сервис — вся логика:** правила, расчёты, транзакции, внешние API через `lib`, постановка задач в очередь. Про HTTP он не знает: не принимает `Context`, не возвращает `Response`. Ошибку бросает своим классом (`new AppError('DEAL_CLOSED', 'Сделка уже закрыта', 409)`), а в ответ её превращает `app.onError`. Поэтому один и тот же сервис зовут роут, воркер, бот и скрипт.
- **Middleware — сквозное:** вход, права, CSRF, лимиты, лог запроса. Бизнес-логики в нём нет.
- **Воркер** решает, когда работать, а что делать — решает сервис: воркер берёт задание и вызывает сервис.
- **lib** — инфраструктура. Не импортирует `services/`, `routes/`, `workers/`.
- Импорты идут в одну сторону: `routes → services → lib`. Сервисы разных разделов могут звать друг друга, но без циклов.
- У сущности с правилами одна функция создания (`createDeal`, `createPayout`). Прямой `prisma.x.create` мимо неё запрещён: созданное в обход не попадёт в уведомления, отчёты и дедуп.
- Списки, на которых держится система (разделы и права, типы уведомлений, этапы), — реестр в одном файле. Меню, проверка прав и редактор прав читают его. Новый раздел — одна строка в реестре.
- Не настроена необязательная внешняя зависимость (S3, бот, почта) — эта функция отвечает 503 с объяснением, остальное работает. Из-за отсутствия ключа к второстепенному сервис не падает.

**Фронт (Nuxt)**

```
app/
  pages/          маршруты: данные из composable, раскладка компонентов
  components/     по папке на раздел: deals/DealCard.vue, deals/DealForm.vue
  composables/    useApi и по composable на раздел: useDeals, useClients
  middleware/     auth.global.ts, permissions.global.ts
  utils/          чистые функции: деньги, даты, подписи статусов
  layouts/        каркас: меню, шапка
```

- **Страница** собирает экран: берёт данные из composable, раскладывает компоненты, держит фильтры в query адреса. В ней нет `$fetch`, расчётов и разметки больших форм.
- **Компонент** — одна вещь на экране: карточка, форма, таблица, вкладка. Данные получает через props, наверх сообщает через emit. Большая карточка — это вкладки отдельными компонентами. Большая форма — компонент формы плюс composable с отправкой.
- **Composable** — запросы к API и состояние раздела: `useDeals` знает список, фильтры, создание и закрытие сделки. В API ходят только composables и только через `useApi`. Прямой `$fetch` или `useFetch` в компоненте или странице запрещён.
- **useApi** — одна обёртка на все запросы: базовый адрес, `credentials: 'include'`, разбор ошибки `{ error: { code, message } }`. 401 → выход и перезагрузка. 403 — не выход, а «нет прав».
- **utils** — чистые функции без Vue и запросов. Подписи статусов, цвета, форматы денег и дат живут здесь в одном экземпляре: подпись, поправленная в одном месте из четырёх, однажды разошлась с остальными.
- **middleware** — вход и права по URL (раздел 6).
- Отдельный стор (Pinia) не нужен, пока хватает composable с `useState`. Глобально живут только пользователь и его права.
- Считает бэкенд, фронт показывает. Суммы, периоды, пороги и «можно ли нажать» приходят от API готовыми полями (`canClose: true`). Бизнес-правила фронт не повторяет.
- **Сайт (SSR)** устроен так же. В его `server/` — только служебное: sitemap, robots, сброс кэша. Данные он берёт из API.

## 5. Данные и миграции

**Миграции**
- Схему меняет только одна последовательность: правка `schema.prisma` → `npx prisma migrate dev --name <что_меняем>`. На проде миграции применяет контейнер при старте (`prisma migrate deploy`).
- **Запрещено:**
  - `db push`, `migrate reset`, `migrate diff`;
  - флаги `--shadow-database-url`, `--accept-data-loss`, `--force-reset`;
  - ручной SQL: `psql`, `$executeRaw`, `$queryRawUnsafe`;
  - правка файлов в `prisma/migrations/`.

  Однажды `migrate diff --shadow-database-url <боевая база>` стёр все таблицы прода: shadow-база для Prisma означает «эту можно затирать».
- Перед `migrate dev` посмотри `git diff prisma/schema.prisma`: Prisma заберёт в миграцию и чужие незакоммиченные правки. Папку миграции коммить вместе с кодом, который на неё опирается.
- Миграции только добавляют. Колонку удаляй позже, отдельной миграцией, когда код её уже не читает. До тех пор держи в CLAUDE.md запись «Убрать потом: колонка X — когда в логе появится Y».
- Перенос данных — идемпотентный скрипт или функция на старте с флагом «сделано» в базе. Скрипт по умолчанию — сухой прогон, запись только с `--commit`; в конце печатает, что не переехало.
- Разработка — в своей локальной базе (Postgres в Docker), а не в боевой. Боевую ассистент смотрит только на чтение: Postgres MCP в `--access-mode restricted` или отдельный пользователь с SELECT.
- Бэкап базы — каждый день, на хранилище вне сервера, и восстановление хотя бы раз проверено. Всё остальное в этом разделе бэкап не заменяет.

**Модель данных**
- Деньги — в целых копейках (`Int`), без float. Единицы переводи на границе: если внешний API отдаёт рубли дробью, конвертируй при приёме.
- Время в базе — UTC. Часовой пояс бизнеса — одна константа и одна утилита. Полночь по Москве не клади в `@db.Date`: Postgres запишет предыдущий день.
- Состояние хранится в колонках, а не подстрокой в тексте. Метка `[reminder]` в поле `note` однажды пережила перенос записи и навсегда выключила по ней напоминания.
- На каждую причину — свой статус. «Отменено человеком» — это не `ERROR` с пояснением: иначе отмены считаются авариями, а сверка их «чинит».
- Статус, который приходит не по порядку (доставлено, прочитано), только растёт: старое событие не откатывает новое.
- Бизнес-параметры (пороги, сроки, тексты, ссылки, этапы) живут в базе, в таблице настроек, и правятся из админки. В env — только секреты и адреса, в коде — значения по умолчанию. Один параметр — один источник: однажды два env разошлись, и одна сущность показывала «0/5» и «0/3».
- Условия сделки (цена, доля, партнёр) записываются в саму сделку, а не вычисляются из текущих настроек.
- Публичные адреса (slug статьи, путь картинки) после публикации не меняются. Если менять всё же нужно — сначала история адресов и 301.
- Пустой ответ внешнего источника не значит «ничего нет». Хорошие данные пустыми не перезаписывай: однажды пустой фид стёр все картинки объявлений.
- Группируй по справочнику, а не по свободному тексту: опечатки дают дубли в отчётах.

**Prisma**
- Хелпер, который вызывают внутри транзакции, принимает `tx`. Второе соединение из пула под открытой транзакцией вешает пул.
- Возможный дубль внутри транзакции — через `createMany({ skipDuplicates: true })`, а не `create` с перехватом P2002: упавший INSERT ломает всю транзакцию.
- `prisma.$disconnect()` при работающем приложении не вызывай.
- Поле, которое фронт может прислать пустым, описывай как `z.string().nullish()`, а не `.optional()`.
- Новое поле проводи через все слои: схема → миграция → Zod → сервис → `select` списка и карточки → тип на фронте → форма. Чаще всего оно теряется в `select` списка.
- Удаляешь ключ из Zod-схемы JSON-поля (например, прав) — оставь его «надгробием». Иначе Zod молча вырежет этот ключ у всех при первом сохранении.

## 6. Безопасность приложения

**Конфиг и секреты**
- env проверяется Zod при старте, при ошибке — `process.exit(1)`. Что проверять:
  - `JWT_SECRET` от 32 символов и не заглушка;
  - нет `*` в CORS вместе с `credentials`;
  - в проде адреса только https;
  - токены от 32 символов;
  - заданы переменные, обязательные для прода.

  Булевы флаги разбирай своей функцией, а не `z.coerce.boolean()`: тот читает `'false'` и `'0'` как true.
- Секреты — только в env приложения в Dokploy. В git лежит `.env.example` без значений. Никогда не клади секрет:
  - в код, CLAUDE.md или `.mcp.json`;
  - в `NUXT_PUBLIC_*` или `runtimeConfig.public`;
  - в логи и в чат с ассистентом.
- В `.dockerignore` — `.env`, `node_modules`, `.git`. Иначе локальная сборка унесёт `.env` в образ.
- Засветил ключ (в коммите, на скриншоте, на стриме) — перевыпусти. Удаление из git не помогает: ключ остаётся в истории.

**Вход и сессия**
- Пароль — bcrypt с cost 12, минимум 12 символов. Хэш делает скрипт, который читает пароль из stdin, а не из аргумента: аргумент останется в истории shell.
- Сессия — JWT в httpOnly-куке с `Secure` и уникальным именем (не `token`), по умолчанию только на хосте API. Параметры куки при входе и выходе одинаковые, иначе выход её не сотрёт.
- На каждом запросе перечитывай пользователя из базы: существует ли он и `is_active`. Сессия гаснет, если выдана раньше смены пароля (`iat < password_changed_at`).
- Кука с `SameSite=None` (фронт и API на разных поддоменах) — значит, на всех мутациях проверяй Origin/Referer по белому списку. Нет заголовков или источник чужой — 403.
- Код входа (второй фактор через Telegram, почту, SMS):
  - 6 цифр из `crypto.randomInt`, не из `Math.random()`;
  - 5 минут, 5 попыток, одноразовый, новый вход гасит старый;
  - сравнение через `timingSafeEqual`;
  - резервные коды хранятся только хэшем.
- Не выдавай, что угадано. На чужой логин или номер отвечай тем же текстом и за то же время, что на свой (пароль сверяй всегда). Причина отказа — в лог, наружу — безликое «неверные данные».
- Лимит попыток по IP: вход, коды, смена пароля, публичные формы. IP бери из первого `X-Forwarded-For`, и только за своим прокси (Traefik в Dokploy). Лимит в памяти годится для одного экземпляра — запиши это допущение в коде рядом.
- Два типа пользователей (сотрудник и клиент) — две разные куки и явный выбор, какую читать. С одной общей кукой клиент однажды оказался «сотрудником» и увидел скрытое.
- У каждого вида JWT своё поле `type`, и проверка пускает только ожидаемые типы: одноразовый тикет не должен проходить как сессия.

**Права**
- Права — матрица «раздел × действие» у пользователя. На каждом серверном маршруте — `requirePermission('section', 'action')`, суперадмин проходит всегда.
- Проверка на фронте — только для удобства (скрыть кнопку). Защищает сервер.
- Опасное действие (войти под другим пользователем, выплатить, удалить) выдаётся отдельным правом, а не ролью.
- На фронте права проверяются по URL в глобальном middleware, а не только в меню: страницы без пункта меню открываются по прямой ссылке.
- `requireRole('ADMIN', 'SUPERADMIN')` при двух ролях — декорация, он пропускает всех. Только права.
- Пройдись по списку маршрутов: каждый маршрут админки без куки отвечает 401.

**Машины: боты, сервисы, интеграции**
- У каждого потребителя свой токен и узкое API: боту — только его маршруты. В базе — sha256 токена, сравнение через `timingSafeEqual`. Пустой токен в env значит, что маршрут выключен (503), а не открыт.
- API-ключи для людей:
  - в базе только хэш, полный ключ показывается один раз;
  - ключ может только сузить права владельца;
  - по умолчанию «только чтение»;
  - управлять ключами можно только из живой сессии.
- Схемы для машин — `.strict()`: лишнее поле даёт 400, а не тихо выбрасывается.

**Вход данных и вывод**
- Zod-схема на каждом маршруте. `req.body` целиком в `create` или `update` не передавай — только перечисленные поля.
- Ошибка наружу — `{ error: { code, message } }` с текстом для человека. Никогда не отдавай `err.message`, стек или SQL. Один глобальный `app.onError`. P2002 превращается в 409 с понятным текстом.
- Лимит тела запроса — 1–2 МБ на всё. Больше — только у маршрутов загрузки.
- Markdown из базы рендери с `html: false`. Всё, что вставляешь в HTML строкой, экранируй. `v-html` с пользовательскими данными нельзя.
- Скачивание по ссылке от пользователя (картинка по URL) — с защитой от SSRF. Регулярки по имени хоста мало: публичный адрес может редиректить на внутренний сервис. Что нужно:
  - только http(s);
  - резолвить DNS и отклонять приватные адреса (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fc00::/7);
  - `redirect: 'manual'` и та же проверка на каждом шаге;
  - таймаут и лимит размера.
- Загрузки: лимит размера, тип проверяется по содержимому, а не по расширению.

**Заголовки**
- `secureHeaders()` в Hono: HSTS, nosniff, без X-Powered-By.
- Админке — `X-Frame-Options: DENY` и `frame-ancestors 'none'`.
- Source map в прод не выкладывай.

**Логи и персональные данные**
- Тела запросов не логируй: туда попадают пароли. При входе в лог идут только логин или телефон и причина отказа.
- Токенов в логах нет. Библиотеки печатают URL с токеном бота — оберни `console` так, чтобы токен вычищался.
- У строк лога — префикс подсистемы, чтобы их можно было грепать: `[auth] 401 BAD_PASSWORD | POST /api/auth/login`, `[worker:payout] ok (120ms) …`.
- Персональные данные — в приватном бакете. PWA ответы API не кэширует. Чужим ролям данные отдаются с маской.

## 7. Деньги и критичные операции

- Сумма фиксируется снимком при создании операции и потом не пересчитывается.
- Статус меняется атомарно с условием: `updateMany({ where: { id, status: 'PENDING' }, data: { status: 'PAID' } })`, затем проверка `count === 1`. Плюс уникальный ключ в журнале движений. Тогда повтор из любого процесса безопасен.
- Ключ идемпотентности для провайдера выводится из id операции детерминированно, а не генерируется заново при повторе.
- Воркер захватывает операцию блокировкой в базе с TTL (`locked_until`), а не в памяти: такая блокировка переживает рестарт и второй экземпляр.
- Вебхук — не единственный источник правды. Воркер сверки добивает зависшие операции через API провайдера.
- 4xx от провайдера — сразу ошибка, без повторов. Сеть и 5xx — повторы с растущей паузой. Через N дней операция получает статус «нужен человек».
- Нет данных для расчёта — нет начисления. Ноль или значение по умолчанию в деньги не подставляй.
- Явно разделяй, из чьих денег сумма: клиента или компании.
- Кнопка «Выплатить» активна по тому же полю, по которому сервер разрешит операцию. Иначе — 400 и модалка с неправильной суммой.

## 8. Вебхуки и внешние API

**Вебхуки**
- Подпись проверяется всегда, HMAC сравнивается через `timingSafeEqual`. Проверь и отрицательный путь: подделанная подпись реально отвергается. Однажды из-за префикса `v1=` подпись не сходилась ни у кого, и принималось всё подряд.
- Если провайдер шлёт timestamp — проверяй свежесть.
- Ответ быстрый, обработка потом: сохранил событие → ответил 200 → разбираешь в очереди.
- Код ответа подбирай под поведение провайдера. Сначала узнай, что он делает на 4xx, 5xx и таймаут. Одни повторяют на 5xx — тогда 503 при сбое записи правильный. Другие на 401/403 отключают endpoint — тогда на плохую подпись отвечай 400.
- Идемпотентность — уникальный ключ события в базе. Буфер в памяти — только ускорение.
- Повторы и синхронизация истории не должны будить людей: уведомляй только о свежем, например за последние 30 минут.

**Исходящие запросы**
- Таймаут на каждом `fetch` (`AbortSignal.timeout`).
- Повторяй только сетевые сбои, 429 (с учётом `retry_after`) и 5xx, и только идемпотентные запросы. 4xx — без повторов. Таймаут после отправки значит, что запрос мог дойти: вслепую не повторяй.
- Разворачивай `err.cause`: голое «fetch failed» не отличает «не нашёлся DNS» от «сервис лежит».
- Пиши в лог, каким путём ушёл запрос: напрямую или через прокси.
- Необязательное действие (уведомление, служебное сообщение) не роняет основное — у него свой try/catch.

**Сеть из России** (сервер или разработчик в РФ)
- Пакеты — с зеркала npmmirror через `.npmrc`. `npm -g` `.npmrc` не читает, ему реестр передаётся флагом. Движки Prisma — через `PRISMA_ENGINES_MIRROR`.
- Сборка и рантайм не ходят в интернет за шрифтами и иконками: всё лежит в бандле.
- Заблокированное (Telegram, OpenAI, Google) — через свой прокси за границей: только CONNECT, логин, белый список хостов. Через прокси идёт только заблокированное, остальное напрямую.
- В Node прокси подключается через `undici` `ProxyAgent` и `dispatcher`. Но grammy ходит через node-fetch и `dispatcher` молча игнорирует, ему нужен `agent`. По логу проверяй, что прокси реально применился.
- Российские банки переходят на сертификаты НУЦ Минцифры. Добавь корневой сертификат в образ (`NODE_EXTRA_CA_CERTS`) и проверь TLS из контейнера тем же путём, каким ходит боевой код.
- У контейнеров IPv4, а некоторые хосты отвечают с сервера только по IPv6. Проверяй `curl -4`, `curl -6` и `fetch` из самого контейнера.

**Telegram-боты**
- На один токен — один процесс. При деплое живут два контейнера, и второй получает 409: жди и повторяй, а не падай.
- Бот — тонкий транспорт: тексты, кнопки и состояние решает бэкенд. Состояние диалога в памяти — только кэш, шаг восстанавливается из базы.
- Вместо `bot.start()` — `run(bot)` + `sequentialize(chat.id)`, чтобы один медленный запрос не стопорил всех. При старте — `drop_pending_updates`.
- `answerCallbackQuery` — сразу, до похода в бэкенд. Кнопки в Telegram живут вечно: на старую кнопку бэкенд отвечает 409, бот гасит клавиатуру и показывает текущий экран.
- Бот входа и бот, который пишет незнакомым людям, — разные боты: жалобы на спам отрежут коды входа.

## 9. Фоновые задачи

- Очередь — таблица в Postgres: статус, попытки, `next_attempt_at`, текст ошибки.
  - Захват атомарный: `updateMany where status = 'QUEUED'` или `FOR UPDATE SKIP LOCKED`.
  - Аренда на N минут с продлением; зависшие задания возвращаются в очередь.
  - На SIGTERM воркер отдаёт задание обратно.
- Тяжёлую работу не держи промисом в памяти: рестарт её потеряет.
- При деплое старый и новый контейнер живут одновременно. Фоновые задачи выполняет только ведущий — тот, кто взял advisory-lock в Postgres (`pg_try_advisory_lock`). Иначе всё уйдёт дважды.
- Расписание (включено или нет, интервал) хранится в базе и правится из админки. На старте воркер запускается, только если с `last_run_at` прошёл его интервал. Иначе каждый деплой гоняет всё подряд: «месячная» платная проверка однажды отработала 12 раз за 15 дней.
- Окна — догоняющие: условие «порог наступил, отметки нет», а не «сейчас … сейчас + 5 минут». Тогда пропущенный тик ничего не теряет. Дедуп ежедневных задач — ключом с датой.
- Что писать в журнал:
  - пустой прогон — не писать;
  - ошибку и ручной запуск — писать всегда;
  - алерт — только на переходе OK → ERROR, а не на каждом тике.
- Уведомления — через outbox: строка пишется в той же транзакции, что и действие, с `dedup_key`, а отправляет её воркер с повторами. Ошибки делятся на временные и окончательные.
- Платный внешний вызов — под блокировкой: два параллельных прогона заплатят дважды.
- Страховочный воркер не трогает «горячие» строки, которые сейчас обрабатывает основной: порог остывания больше интервала. Однажды сверка и воркер выплат просыпались в одну миллисекунду, и выплата 17 часов стояла без единой ошибки.
- Плавная остановка: дождись текущих запросов и задач (до 25 секунд при grace period 30).
- В разработке воркеры по умолчанию выключены (`WORKERS_ENABLED=false`).

## 10. Фронтенд: поведение

- Ошибку показывай текстом сервера. Ошибку загрузки не глуши `console.error`: человек должен видеть, что данные не пришли.
- Фильтры и открытая карточка — в query адреса (`?status=new&id=42`): ссылкой можно поделиться, кнопка «назад» работает.
- Состояние, которое видит человек (прочитано, колонки таблицы, вид), хранится на сервере у учётки, а не в localStorage. Иначе оно привязано к устройству.
- Незнакомое значение с сервера показывай его ключом, а не прячь.
- Разрушающее действие — через модалку подтверждения. Изменение, которое уходит во внешнюю систему, — через модалку «было → станет».
- Длинный текст:
  - явная кнопка «Сохранить», Cmd/Ctrl+S и предупреждение при уходе со страницы;
  - сохранения идут одной очередью, чтобы ответ на старый запрос не перебил свежую правку.
- Ширина 390 px проверена. Отступы задаёт страница.
- Tailwind-классы — литеральными строками, не склейкой: сканер вырежет склеенное.
- PWA:
  - `registerType: 'prompt'`;
  - кэшируется только оболочка приложения, ответы API — нет: данные устаревают, а персональные данные оседают в Cache Storage;
  - после сборки проверь, что `sw.js` на месте и устанавливается.
- Публичный SSR-сайт:
  - кэш страниц (`swr`) — с пределом LRU: ключ кэша включает `?query`, и скрипт с `/?x=1..3000` иначе забьёт память;
  - браузеру — `no-cache`;
  - при публикации кэш сбрасывается запросом с секретом;
  - env читается при старте, а не запекается в образ.

## 11. Деплой: Dokploy на одном сервере

Весь продукт живёт на одном VPS с Dokploy: приложения, база, домены, HTTPS, бэкапы. Dokploy — это Docker Swarm и Traefik с понятной панелью:
- пуш в `main` → он сам собирает образ по Dockerfile и выкладывает новую версию;
- сам выпускает и продлевает сертификаты Let's Encrypt;
- поднимает Postgres и делает его бэкапы в S3;
- показывает логи, env и ресурсы каждого приложения.

Для этого масштаба это всё, что дал бы Kubernetes, но без Kubernetes.

- **Не пиши:** манифесты Kubernetes, Helm-чарты, Terraform, GitHub Actions для сборки и выкладки, деплой скриптом по SSH, docker-compose руками на сервере. Проверки (сборка, тесты) в GitHub Actions можно, выкладка — дело Dokploy.
- **Репозиторий:** один на продукт, в нём папка на каждый деплоящийся сервис (`api/`, `admin/`, `site/`) со своим Dockerfile. В Dokploy у каждой папки своё приложение: Build Path — путь к папке, Watch Paths — чтобы пуш в `admin/` не пересобирал API.
- **База:** сервис Postgres в том же Dokploy. Приложения ходят к ней по внутреннему имени (`<appName>:5432`), External Port пустой.
- **Домен:** A-запись на сервер → домен у приложения в Dokploy с HTTPS.
- **Секреты:** в env приложения в Dokploy, больше нигде.
- **Тестовый стенд**, если нужен, — второе приложение в том же Dokploy с веткой `dev` и своей базой. Для внутреннего продукта на несколько человек часто не нужен.
- **Dockerfile** у каждого сервиса:
  - multi-stage, в финальный образ — только сборка;
  - `USER node`;
  - `pnpm install --frozen-lockfile`;
  - `.dockerignore`.
- Healthcheck ходит в базу (`SELECT 1`), а не отвечает `ok` всегда: иначе мёртвый Prisma не заметен.
- При выкладке старый и новый контейнер какое-то время живут вместе: отсюда правила о ведущем воркере (раздел 9) и о боте (раздел 8).
- Порядок выкладки: если добавились поля, сначала API, потом фронты.
- Лимит памяти и CPU у каждого приложения подбирается по `memory.peak` под нагрузкой.
- Адреса для фронта — через `runtimeConfig.public` и env приложения в Dokploy (`NUXT_PUBLIC_API_BASE`). Nuxt читает их при старте контейнера, пересобирать ради смены адреса не нужно. В `public` — только то, что можно показать любому.
- Защита сервера и панели — `docs/server.md`.

## 12. CLAUDE.md проекта

- В корне — карта: масштаб, какие сервисы, стек, порт, где правила. В каждом сервисе — свой CLAUDE.md (правила, подводные камни, состояние) и README.md (карта кода: структура, таблицы, маршруты, env), чтобы не сканировать код заново.
- Правило — одна фраза + почему + путь к файлу. Для подводного камня — ещё дата и что случилось.
- Хвосты держи в разделе «Что осталось» по группам: «руками владельцу», «ждёт приёмки», «доделать в коде», «убрать потом» (с условием), «отказались».
- Задачи — в одном месте (доска или issues), а не россыпью TODO по коду.
- Нет CLAUDE.md — предложи создать его по шаблону, начиная с масштаба, прежде чем писать много кода.
