# База — как проектировать схему

PostgreSQL 17 через Prisma 6 (`prisma@6 @prisma/client@6`, с номером версии). Схему держит только API и меняет её только миграциями. Здесь — как проектировать таблицы, чтобы через год не переделывать.

## Как менять схему

1. Правишь `schema.prisma`.
2. Смотришь `git diff prisma/schema.prisma`: Prisma заберёт в миграцию и чужие незакоммиченные правки.
3. `npx prisma migrate dev --name <что_меняем>` — в локальную базу (`docker compose up -d db` в корне проекта).
4. Коммитишь схему и папку новой миграции вместе с кодом, который на неё опирается.

На прод миграцию накатывает деплой: `prisma migrate deploy` при старте контейнера. Ничего другого: ни `db push`, ни `migrate reset`, ни ручного SQL, ни правки файлов в `migrations/`. Prisma заговорила про `reset`, `drift` или потерю данных — остановись и спроси владельца.

Все адреса в блоке `datasource` — `url`, `directUrl`, `shadowDatabaseUrl` — смотрят только в локальную базу. `shadowDatabaseUrl` — это база, которую Prisma затирает при каждом `migrate dev`: укажешь в ней боевую — потеряешь боевую. Туннель к боевой базе на `localhost` — всё равно боевая база. Хук сверяет адрес с `docker-compose.yml` в корне: хост, порт и имя базы.

## Когда схема Prisma не умеет

Частичный уникальный индекс (`email` уникален только среди неархивных), триггер, расширение Postgres, `CHECK` — схемой Prisma 6 не описываются. Это ручная миграция. Хук не даст сделать её ассистенту, и это правильно: её делает владелец.

1. Ассистент пишет владельцу SQL и объяснение простыми словами: что делает, почему схемой нельзя, как откатить.
2. Владелец в своём терминале: `npx prisma migrate dev --create-only --name <что>`. Prisma создаст пустую миграцию и не применит её.
3. Владелец вставляет SQL в конец созданного `migration.sql`, читает файл целиком и запускает `npx prisma migrate dev`.
4. Рядом с моделью в схеме — комментарий: `/// частичный индекс deals_email_active — ручная миграция <имя>`. Иначе следующая сессия не узнает, что он есть.

## Таблицы

- Названия — по-английски и в одном стиле по всей схеме. Модель — в единственном числе: `Deal`, `Client`.
- У каждой таблицы — `id`, `createdAt`, `updatedAt`.
- Последовательный `id` наружу в публичных ссылках не показывай: его перебирают подряд. Для публичной ссылки — отдельное поле `token` или `slug`.
- Связи — внешними ключами (`@relation`), а не id в тексте или JSON.
- Уникальность — в базе (`@unique`, `@@unique`), а не только проверкой в коде: два одновременных запроса проверку в коде проходят оба.
- Индекс — на каждое поле, по которому ищешь, фильтруешь или сортируешь списки, и на внешние ключи: Postgres сам их не индексирует.
- Сущности, на которые ссылаются деньги, история и отчёты (клиент, сделка, сотрудник), не удаляются, а архивируются: `archivedAt`. Иначе отчёты за прошлый год сломаются.

## Статусы и состояние

- Статус — `enum`. На каждую причину — свой статус: «отменено человеком» — не `ERROR` с пояснением. Иначе отмены считаются авариями, а сверка их «чинит».
- Состояние хранится в колонках, а не подстрокой в тексте. Метка `[reminder]` в поле `note` однажды пережила перенос записи и навсегда выключила по ней напоминания.
- Статус, который приходит не по порядку (доставлено, прочитано), только растёт: старое событие не откатывает новое.
- Важные изменения (статус сделки, сумма, ответственный) пишутся в журнал: кто, когда, было → стало.

## Деньги и время

- Деньги — в целых копейках, без float. Внешний API отдаёт рубли дробью — конвертируй при приёме.
- `Int` вмещает до 2 147 483 647 копеек — это около 21,4 млн ₽. Сумма больше — Postgres отвергнет запись с ошибкой. Может одна сумма или итог в колонке перерасти 20 млн ₽ (недвижимость, крупный B2B, накопительные итоги) — бери `BigInt`. Prisma отдаёт его типом `bigint`, на котором `JSON.stringify` падает: на выходе из API переводи в `Number` (точно до 90 трлн ₽).
- Время — UTC. Часовой пояс бизнеса — одна константа и одна утилита в коде. Полночь по Москве не клади в `@db.Date`: Postgres запишет предыдущий день.
- Условия сделки (цена, доля, партнёр) записываются в саму сделку, а не вычисляются из текущих настроек: настройки поменяются, а старая сделка — нет.

## Справочники и настройки

- Группируй по справочнику (таблица или `enum`), а не по свободному тексту: опечатки дают дубли в отчётах.
- Бизнес-параметр, который владелец будет менять сам (тексты, этапы, пороги, ссылки), — в таблице настроек, правится из админки. Остальные — константы в одном файле кода. Владелец попросил менять константу без выкладки — переносишь её в настройки. В env — только секреты и адреса. Один параметр — один источник: однажды два env разошлись, и одна сущность показывала «0/5» и «0/3».
- JSON-колонка — только для того, по чему не ищут и не фильтруют. У неё есть Zod-схема. Удаляешь ключ из схемы — оставь его «надгробием», иначе Zod молча вырежет этот ключ у всех при первом сохранении.
- Публичные адреса (slug статьи, путь картинки) после публикации не меняются. Если менять всё же нужно — сначала история адресов и 301.

## Персональные данные

- Что требует закон (хранение в России, согласие, утечки) — `AGENTS.md` в корне, «Персональные данные и закон».
- Храни только то, что нужно для работы продукта.
- Согласие на обработку — запись в базе: кто, когда, на какую версию текста согласился.
- Документы и сканы — в приватном бакете S3, в базе — только ключ файла.
- Пустой ответ внешнего источника не значит «ничего нет»: хорошие данные пустыми не перезаписывай. Однажды пустой фид стёр все картинки объявлений.

## Миграции

- Миграции только добавляют. Колонку удаляй позже, отдельной миграцией, когда код её уже не читает. До тех пор держи в CLAUDE.md запись «Убрать потом: колонка X — когда в логе появится Y».
- Перенос данных — идемпотентный скрипт или функция на старте с флагом «сделано» в базе. Скрипт по умолчанию — сухой прогон, запись только с `--commit`. В конце печатает, что не переехало.
- Новое поле проводи через все слои: схема → миграция → Zod → сервис → `select` списка и карточки → тип на фронте → форма. Чаще всего оно теряется в `select` списка.

## Боевая база

- Живёт в Dokploy, наружу не открыта. Ассистент смотрит в неё только на чтение и только через MCP к базе: в режиме `--access-mode restricted` или под пользователем базы с правом SELECT. `psql` хук не пустит.
- Бэкап — каждый день, на хранилище вне сервера, восстановление проверено (`docs/server.md`).
