# API — как устроен и по каким принципам строится

Бэкенд проекта: Node 24, TypeScript `strict`, Hono 4, Zod, Prisma 6 (ставится с номером: `prisma@6 @prisma/client@6`), PostgreSQL 17. Один API на весь продукт: в него ходят админка, сайт и боты. Он же — единственный владелец базы.

Здесь — как строить этот сервис. Как проектировать таблицы — `prisma/AGENTS.md`. Общее для проекта (масштаб, болезни, миграции, секреты, деплой) — `AGENTS.md` в корне.

## Раскладка

```
src/
  index.ts       запуск: проверка env, сервер, воркеры, плавная остановка
  app.ts         сборка: middleware, маршруты, app.onError
  routes/        HTTP: по файлу на раздел — deals.ts, clients.ts
  services/      логика: по папке на раздел — deals/, clients/
  middleware/    вход, права, CSRF, лимиты
  workers/       фоновые задачи и их менеджер
  lib/           env, prisma, fetch с таймаутом, логгер, S3, AppError
prisma/
  schema.prisma  схема базы
  migrations/    миграции — только через prisma migrate dev
scripts/
  check-architecture.mjs   сторож раскладки и размеров
```

## Слои: кто что делает

Запрос идёт сверху вниз: **роут → сервис → lib**. Импортов в обратную сторону нет.

**Роут** только принимает запрос: схема Zod → права → вызов одного сервиса → ответ.

```ts
deals.post('/', requirePermission('deals', 'create'), zValidator('json', createDealSchema), async (c) => {
  const deal = await createDeal(c.get('user'), c.req.valid('json'))
  return c.json(deal, 201)
})
```

В роуте нет запросов к базе, расчётов, циклов по данным, вызовов внешних API и отправки уведомлений. Роут длиннее 15 строк — значит, логика утекла в него.

**Сервис** — вся логика: правила, расчёты, транзакции, внешние API через `lib`, постановка задач в очередь.
- Про HTTP не знает: не принимает `Context` и не возвращает `Response`. Поэтому один и тот же сервис зовут роут, воркер, бот и скрипт.
- Ошибку бросает своим классом: `throw new AppError('DEAL_CLOSED', 'Сделка уже закрыта', 409)`. В ответ её превращает один общий `app.onError`.
- Сервисы разных разделов могут звать друг друга, но без циклов.

**Middleware** — то, что нужно многим маршрутам: вход, права, CSRF, лимиты, лог запроса. Бизнес-логики в нём нет.

**Воркер** решает, когда работать. Что делать — решает сервис: воркер берёт задание и вызывает его.

**lib** — инфраструктура, о домене не знает. Не импортирует `services/`, `routes/`, `workers/`.

## Размеры

- Файл — до 300 строк. 600 — потолок: такой файл режь.
- Функция — до 50 строк, роут — до 15.
- Режь по смыслу: `deals/create.ts`, `deals/close.ts`, `deals/report.ts`. Не `part2.ts` и не `utils2.ts`.
- Имя файла говорит, что внутри.

## Сторож

`scripts/check-architecture.mjs` — скрипт, который читает весь `src/` (нет `src/` — корень сервиса) и проверяет пять правил:
- роут не импортирует prisma (`lib/prisma`, `lib/db`, `@prisma/client`) — в базу ходит только сервис;
- в роуте нет `fetch` и `axios` — внешние API зовёт сервис через `lib`;
- `lib/` не импортирует сервисы, роуты и воркеры;
- сервис и воркер не импортируют роуты;
- нет файлов длиннее 600 строк (длиннее 300 — предупреждение).

Импорты он понимает любые: без расширения, через `@/` и `~/`, через пути из `tsconfig.json`. Всё остальное из этого файла — длину роута, расчёты в нём, права на маршрутах — сторож не видит: это держится на тебе.

Подключение — в `package.json`:

```json
"scripts": {
  "check:arch": "node scripts/check-architecture.mjs",
  "check": "pnpm build && pnpm check:arch"
}
```

`pnpm check` — перед каждым коммитом. Нашёл нарушение — коммит не делаем, чиним код. Правила сторожа не ослабляй, чтобы проверка прошла.

## Конфиг

- env проверяется Zod при старте (`lib/env.ts`), при ошибке — `process.exit(1)`. Что проверять:
  - `JWT_SECRET` от 32 символов и не заглушка;
  - нет `*` в CORS вместе с `credentials`;
  - в проде адреса только https;
  - заданы переменные, обязательные для прода.
- Булевы флаги разбирай своей функцией, а не `z.coerce.boolean()`: тот читает `'false'` и `'0'` как true.
- Код читает env только через `lib/env.ts`, а не `process.env` по всему проекту.
- Необязательная зависимость (S3, бот, почта) не настроена — эта функция отвечает 503 с объяснением, остальное работает. Из-за отсутствия ключа к второстепенному сервис не падает.

## Сущности

- У сущности с правилами одна функция создания (`createDeal`, `createPayout`). `prisma.x.create` мимо неё запрещён: созданное в обход не попадёт в уведомления, отчёты и дедуп.
- Списки, на которых держится система (разделы и права, типы уведомлений, этапы), — реестр в одном файле. Меню, проверка прав и редактор прав читают его. Новый раздел — одна строка в реестре.
- Бизнес-параметр, который владелец будет менять сам (тексты, этапы, пороги), — в таблице настроек, правится из админки. Остальные — константы в одном файле (`lib/config.ts`). Владелец попросил менять константу без выкладки — переносишь её в настройки. В env — только секреты и адреса (`prisma/AGENTS.md`).

**Prisma в коде**
- Хелпер, который вызывают внутри транзакции, принимает `tx`. Второе соединение из пула под открытой транзакцией вешает пул.
- Возможный дубль внутри транзакции — через `createMany({ skipDuplicates: true })`, а не `create` с перехватом P2002: упавший INSERT ломает всю транзакцию.
- В списках — `select` только нужных полей, а не вся строка со всеми связями.
- `prisma.$disconnect()` при работающем приложении не вызывай.

## Запросы и ответы

- Zod-схема на каждом маршруте. `req.body` целиком в `create` или `update` не передавай — только перечисленные поля.
- Поле, которое фронт может прислать пустым, — `z.string().nullish()`, а не `.optional()`.
- Ошибка наружу — `{ error: { code, message } }` с текстом для человека. Никогда не отдавай `err.message`, стек или SQL. P2002 превращается в 409 с понятным текстом.
- Сырой SQL — только `$queryRaw` тегированным шаблоном: значения подставляются параметрами. Склейка строк и `$queryRawUnsafe` — путь к SQL-инъекции.
- Лимит тела запроса — 1–2 МБ. Больше — только у маршрутов загрузки.
- Считает API, фронт показывает. Суммы, периоды, пороги и «можно ли нажать» отдавай готовыми полями (`canClose: true`).
- Списки — с пагинацией и лимитом. Ответ «все 50 тысяч строк» однажды положит и API, и браузер.
- `/health` делает `SELECT 1` в базу, а не отвечает `ok` всегда: иначе мёртвый Prisma не заметен.

## Файлы

- Файлы пользователей — в S3, а не на диске контейнера: при каждом деплое контейнер пересоздаётся, и всё, что лежало на его диске, пропадает.
- В базе — только ключ файла в бакете, не сам файл.
- Персональные данные (паспорта, договоры) — в приватном бакете, отдаются по временной ссылке после проверки прав.
- Загрузка: лимит размера, тип проверяется по содержимому, а не по расширению.
- Скачивание по ссылке от пользователя — с защитой от SSRF. Регулярки по имени хоста мало: публичный адрес может редиректить на внутренний сервис, а DNS — ответить внутренним адресом уже после проверки. Нужно:
  - только http(s);
  - проверять адрес, к которому реально подключаешься, а не тот, что резолвил заранее: свой `lookup` у агента undici (`new Agent({ connect: { lookup } })`), который отклоняет закрытые сети;
  - закрытые сети — через встроенный `net.BlockList`: 0.0.0.0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.168/16, 198.18/15, 224/4, 240/4, ::, ::1, fc00::/7, fe80::/10 и IPv4 внутри IPv6 (`::ffff:127.0.0.1`);
  - `redirect: 'manual'` и та же проверка на каждом шаге;
  - таймаут и лимит размера.

## Вход и права

**Сессия**
- Пароль — bcrypt с cost 12, минимум 12 символов. Только асинхронные `bcrypt.hash` и `bcrypt.compare`: `hashSync` и `compareSync` останавливают весь API на время расчёта. Хэш для первого админа делает скрипт, который читает пароль из stdin, а не из аргумента: аргумент останется в истории shell.
- Сессия — JWT в httpOnly-куке с `Secure` и уникальным именем (не `token`), по умолчанию только на хосте API. Параметры куки при входе и выходе одинаковые, иначе выход её не сотрёт.
- На каждом запросе перечитывай пользователя из базы: существует ли он и `is_active`. Сессия гаснет, если выдана раньше смены пароля (`iat < password_changed_at`).
- Отзыв сессий: у пользователя есть `sessionVersion`, она же лежит в JWT. Не совпала — 401. «Выйти на всех устройствах», смена пароля и блокировка увеличивают версию, и все старые токены, в том числе украденный, гаснут сразу. Пользователь и так перечитывается на каждом запросе, так что это одна колонка и одно сравнение.
- `SameSite`: фронт и API на поддоменах одного домена (`admin.example.ru` и `api.example.ru`) — это один сайт, хватает `Lax`. `None` нужен, только если фронт и API на разных доменах.
- На всех мутациях проверяй Origin/Referer по белому списку. Нет заголовков или источник чужой — 403. С `Lax` это защита от соседних поддоменов, с `None` — единственная защита от CSRF.
- Код входа (второй фактор через Telegram, почту, SMS): 6 цифр из `crypto.randomInt`, 5 минут, 5 попыток, одноразовый, новый вход гасит старый. Сравнение через `timingSafeEqual`, резервные коды — только хэшем.
- Не выдавай, что угадано: на чужой логин отвечай тем же текстом и за то же время, что на свой. Причина отказа — в лог, наружу — «неверные данные».
- Лимит попыток по IP: вход, коды, смена пароля, публичные формы. Лимит в памяти годится для одного экземпляра — запиши это допущение в коде рядом.
- IP клиента — из `X-Forwarded-For`. В Dokploy Traefik по умолчанию выбрасывает присланный клиентом заголовок и пишет свой, поэтому первый адрес в нём — настоящий. Это перестаёт быть правдой, если перед сервером стоит Cloudflare или другой CDN и его адреса вписаны в доверенные у Traefik (`forwardedHeaders.trustedIPs`): тогда первый адрес подделывается, и лимит входа обходится сменой заголовка. В такой схеме бери крайний справа адрес, который не принадлежит CDN. `X-Real-IP` тоже не спасёт: через CDN его можно прислать поддельным.
- Сотрудник и клиент — две разные куки и явный выбор, какую читать. С одной общей кукой клиент однажды оказался «сотрудником» и увидел скрытое.
- У каждого вида JWT своё поле `type`, проверка пускает только ожидаемые: одноразовый тикет не должен проходить как сессия.

**Права**
- Права — матрица «раздел × действие» у пользователя. На каждом маршруте — `requirePermission('section', 'action')`, суперадмин проходит всегда.
- Проверка на фронте — только удобство. Защищает сервер.
- Опасное действие (войти под другим пользователем, выплатить, удалить) выдаётся отдельным правом, а не ролью.
- `requireRole('ADMIN', 'SUPERADMIN')` при двух ролях — декорация, он пропускает всех. Только права.
- Пользователь видит только своё: в запросе к базе всегда условие на владельца или права, а не «нашли по id — отдали». Иначе чужую запись открывают подбором id.
- Каждый закрытый маршрут без куки отвечает 401 — пройдись по списку.

**Машины: боты, сервисы, интеграции**
- У каждого потребителя свой токен и узкий набор маршрутов. В базе — sha256 токена, сравнение через `timingSafeEqual`. Пустой токен в env — маршрут выключен (503), а не открыт.
- API-ключи для людей: в базе только хэш, полный ключ показывается один раз; ключ может только сузить права владельца; по умолчанию «только чтение».
- Схемы для машин — `.strict()`: лишнее поле даёт 400, а не тихо выбрасывается.

**Заголовки**
- `secureHeaders()` в Hono: HSTS, nosniff, без X-Powered-By.
- CORS — только свои адреса из env, никакой `*` вместе с куками.

## Логи

- Тела запросов не логируй: туда попадают пароли. При входе в лог идут только логин и причина отказа.
- Токенов в логах нет. Библиотеки печатают URL с токеном бота — оберни `console` так, чтобы токен вычищался.
- У строки лога — префикс подсистемы: `[auth] 401 BAD_PASSWORD | POST /api/auth/login`, `[worker:payout] ok (120ms) …`.
- Чужим ролям персональные данные отдаются с маской.

## Деньги — если они есть

- Сумма фиксируется снимком при создании операции и потом не пересчитывается.
- Статус меняется атомарно с условием: `updateMany({ where: { id, status: 'PENDING' }, data: { status: 'PAID' } })`, затем проверка `count === 1`. Плюс уникальный ключ в журнале движений. Тогда повтор из любого процесса безопасен.
- Ключ идемпотентности для провайдера выводится из id операции, а не генерируется заново при повторе.
- Воркер захватывает операцию блокировкой в базе с TTL (`locked_until`), а не в памяти.
- Вебхук — не единственный источник правды. Воркер сверки добивает зависшие операции через API провайдера.
- 4xx от провайдера — сразу ошибка, без повторов. Сеть и 5xx — повторы с растущей паузой. Через N дней операция получает статус «нужен человек».
- Нет данных для расчёта — нет начисления. Ноль или значение по умолчанию в деньги не подставляй.
- Явно разделяй, из чьих денег сумма: клиента или компании.

## Вебхуки и внешние API

**Вебхуки**
- Подпись проверяется всегда, HMAC — через `timingSafeEqual`. Проверь и отрицательный путь: подделанная подпись реально отвергается. Однажды из-за префикса `v1=` подпись не сходилась ни у кого, и принималось всё подряд.
- Провайдер шлёт timestamp — проверяй свежесть.
- Ответ быстрый, обработка потом: сохранил событие → ответил 200 → разбираешь в очереди.
- Код ответа подбирай под поведение провайдера: одни повторяют на 5xx, другие на 401/403 отключают endpoint. Сначала узнай, потом выбирай.
- Идемпотентность — уникальный ключ события в базе.
- Повторы и синхронизация истории не будят людей: уведомляй только о свежем, например за последние 30 минут.

**Исходящие запросы**
- Каждый внешний сервис — своя обёртка в `lib/` (`lib/telegram.ts`, `lib/payments.ts`): адрес, ключ, таймаут, разбор ошибок в одном месте.
- Таймаут на каждом `fetch` (`AbortSignal.timeout`).
- Повторяй только сетевые сбои, 429 (с учётом `retry_after`) и 5xx, и только идемпотентные запросы. Таймаут после отправки значит, что запрос мог дойти: вслепую не повторяй.
- Разворачивай `err.cause`: голое «fetch failed» не отличает «не нашёлся DNS» от «сервис лежит».
- Необязательное действие (уведомление) не роняет основное — у него свой try/catch.

**Telegram-боты**
- **Бот — вебхуком внутри API.** Маршрут `/telegram/<секрет>`, grammy `webhookCallback(bot, 'hono', { secretToken })`, при регистрации вебхука — тот же `secret_token`: Telegram пришлёт его в заголовке `X-Telegram-Bot-Api-Secret-Token`. Так отдельный процесс не нужен, при деплое нет 409, а если API лежал, Telegram сам повторит доставку.
- Вебхук отвечает быстро: долгое (рассылка, запрос к ИИ) — в очередь.
- Бот — тонкий транспорт: тексты, кнопки и состояние решают сервисы этого API. Состояние диалога в памяти — только кэш, шаг восстанавливается из базы.
- `answerCallbackQuery` — сразу. Кнопки в Telegram живут вечно: на старую кнопку отвечай 409, гаси клавиатуру и показывай текущий экран.
- Long-polling — только если сервер недоступен Telegram снаружи. Тогда: на один токен — один процесс; при деплое второй контейнер получает 409 — жди и повторяй, а не падай; `run(bot)` + `sequentialize(chat.id)` вместо `bot.start()`.
- `drop_pending_updates` — только для бота, которому старые сообщения не нужны (коды входа). Бот с заявками накопленное не выбрасывает: это потерянные клиенты.
- Бот входа и бот, который пишет незнакомым людям, — разные боты: жалобы на спам отрежут коды входа.

## Фоновые задачи

- Очередь — таблица в Postgres: статус, попытки, `next_attempt_at`, текст ошибки. Захват атомарный (`updateMany where status = 'QUEUED'` или `FOR UPDATE SKIP LOCKED`), аренда на N минут, зависшие задания возвращаются в очередь, на SIGTERM задание отдаётся обратно.
- Тяжёлую работу не держи промисом в памяти: рестарт её потеряет.
- При деплое старый и новый контейнер живут одновременно. Фоновые задачи выполняет только ведущий, иначе всё уйдёт дважды. Ведущий — строка-аренда в таблице (`name`, `holder`, `expiresAt`): захват — `updateMany` с условием «аренда истекла или она уже моя», продление каждые 10 секунд, срок — 30. Advisory-lock через Prisma не годится: замок держится на одном соединении пула, а Prisma не обещает, через какое соединение пойдёт следующий запрос. Соединение пересоздалось — замок тихо снялся, и ведущих стало два.
- Расписание хранится в базе. На старте воркер запускается, только если с `last_run_at` прошёл его интервал. Иначе каждый деплой гоняет всё подряд: «месячная» платная проверка однажды отработала 12 раз за 15 дней.
- Окна — догоняющие: «порог наступил, отметки нет», а не «сейчас … сейчас + 5 минут». Дедуп ежедневных задач — ключом с датой.
- В журнал: пустой прогон — не писать; ошибку и ручной запуск — всегда; алерт — только на переходе OK → ERROR.
- Уведомления — через outbox: строка пишется в той же транзакции, что и действие, с `dedup_key`, отправляет её воркер с повторами.
- Платный внешний вызов — под блокировкой: два параллельных прогона заплатят дважды.
- Страховочный воркер не трогает строки, которые сейчас обрабатывает основной. Однажды сверка и воркер выплат просыпались в одну миллисекунду, и выплата 17 часов стояла без единой ошибки.
- Плавная остановка по SIGTERM: перестань брать новые задания, отдай взятые обратно в очередь, дождись текущих запросов и закрой соединения. Уложись в 8 секунд: через 10 Docker убивает процесс. Нужно дольше — выставь Stop Grace Period в настройках Swarm приложения в Dokploy.
- В разработке воркеры выключены (`WORKERS_ENABLED=false`).
