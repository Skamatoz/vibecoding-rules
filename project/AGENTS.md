# Правила разработки

Версия правил: 2026-11-24 · https://github.com/Skamatoz/vibecoding-rules

Правила для ИИ-ассистента (Claude Code, Codex, Cursor), который строит этот проект. Они собраны из живых проектов: CRM с платежами и выплатами, чат-платформы для продаж, сайта с админкой. Почти каждое правило — ответ на то, что однажды уже сломалось.

Правила лежат в нескольких файлах:

| Файл | Что в нём | Когда читать |
|---|---|---|
| `AGENTS.md` (этот) | общее: масштаб, болезни, архитектура, код, база, секреты, закон, деплой | всегда |
| `CLAUDE.md` в корне | этот проект: что за продукт, масштаб, сервисы | всегда |
| `api/AGENTS.md` | как строить бэкенд: слои, роуты, сервисы, middleware, права, фоновые задачи | перед работой в `api/` |
| `api/prisma/AGENTS.md` | как проектировать базу: таблицы, связи, индексы, миграции | перед правкой схемы |
| `admin/AGENTS.md` | как строить админку (SPA): страницы, компоненты, composables, плагины, middleware | перед работой в `admin/` |
| `site/AGENTS.md` | как строить публичный сайт (SSR): то же плюс SEO и кэш | перед работой в `site/` |
| `docs/server.md` | сервер и Dokploy: установка, защита, бэкапы, наблюдение | когда дело доходит до сервера |

Рядом с каждым `AGENTS.md` в папке сервиса лежит `CLAUDE.md` из одной строки `@AGENTS.md`: так эти правила видят и Codex с Cursor, и Claude Code.

Если правило противоречит CLAUDE.md проекта, прав CLAUDE.md. Если правило мешает задаче, скажи об этом владельцу, а не обходи молча.

## 0. Владелец и как с ним работать

Владелец может не быть программистом. Он знает, что должен делать продукт, но не всегда понимает, как устроен код.

- Объясняй решения простыми словами: что сделал, зачем, что это меняет для него.
- Не знаешь, чего он хочет, — спроси. Не знаешь, как устроен внешний API, — сверься с документацией или спроси. Выдуманное хуже вопроса.
- Необратимое и внешнее — только по его прямому слову: удаление данных, публикация, рассылка, платёж, DNS, настройки сервера и Dokploy, перевыпуск ключей.
- Делай то, о чём просили. Попутно не переписывай, не переименовывай и не переформатируй чужое: такие правки ломают несвязанное. Увидел проблему — напиши о ней.
- Большую задачу начинай с плана: что меняем, какие файлы, как проверить, как откатить. Код — после согласия.
- Работай маленькими шагами: шаг → `pnpm check` → проверка руками → коммит.
- В проекте должен быть включён git-хук `.githooks/pre-commit`: он запускает сторожа и ищет секреты перед каждым коммитом. Проверь `git config core.hooksPath` — должно быть `.githooks`. Нет — выполни `git config core.hooksPath .githooks` (и `chmod +x .githooks/pre-commit`, если хук не запускается).
- Проверки не обходят. `git commit --no-verify`, смена `core.hooksPath`, правка хуков и сторожей, чтобы прошло, — запрещены. `@ts-ignore`, `as any`, `eslint-disable`, пустой `catch`, удалённый тест — тоже не починка. Не проходит — чини причину или скажи владельцу.
- Хук Claude Code заблокировал команду — не обходи его другим флагом, скриптом или подменой env. Скажи владельцу, что хотел сделать и зачем. Некоторые вещи делает только он сам — например, ручную миграцию (`api/prisma/AGENTS.md`).
- Коммить только свои файлы: перед коммитом `git status` и `git diff`.
- Поменял поведение — поправь CLAUDE.md или AGENTS.md сервиса в том же коммите. Устаревшая документация вреднее отсутствующей: следующая сессия ей поверит.
- Цифры и факты — только из источников. Не проверил — так и скажи.

## 1. Масштаб: маленький продукт, а не корпорация

По привычке ты проектируешь так, будто у продукта миллионы пользователей и сто разработчиков. Здесь это не так. Масштаб записан в CLAUDE.md проекта. Нет его — спроси, прежде чем проектировать.

Если не сказано другое, проект такой:
- продукт для малого бизнеса или своей команды: CRM, ERP, учёт, склад, запись, кабинет клиента, бот, сайт с админкой;
- от единиц до нескольких тысяч пользователей, обычно меньше десятка запросов в секунду;
- база до десятков миллионов строк;
- один-два человека с ИИ-ассистентом;
- один VPS с Dokploy.

Что из этого следует:
- Один сервер с Postgres держит такой продукт с большим запасом. Тормозит — почти всегда виноват запрос без индекса или выборка лишних полей, а не «нужен кластер».
- Сложность добавляется под измеренную проблему (лог, метрика, медленный запрос), а не «на вырост».
- Слои «на будущее» не нужны: интерфейс с одной реализацией, репозиторий поверх Prisma, DI-контейнер, фабрики, классы use-case, «порты и адаптеры». Функция в сервисе и вызов Prisma в ней.
- Предлагаешь решение — скажи, сколько оно добавляет: сервисов, зависимостей, мест, где может сломаться ночью.

Без измеренной причины и без согласия владельца не предлагай:

| Хочется | Вместо этого | Когда это оправдано |
|---|---|---|
| Kubernetes, Helm, Terraform, свой CI для выкладки | Dokploy: пуш в `main`, он сам собирает и выкладывает | несколько серверов и человек, который их ведёт |
| Микросервисы | один API с разделами внутри | только другое место запуска или сеть («Архитектура») |
| Kafka, RabbitMQ, BullMQ | таблица-очередь в Postgres | сотни заданий в секунду постоянно |
| Redis для кэша и сессий | индекс, `select` нужных полей, кэш в памяти процесса | замерено, что база не справляется, хотя индексы есть |
| Elasticsearch | полнотекстовый поиск Postgres, `pg_trgm` | миллионы документов и релевантность, которой нет в Postgres |
| GraphQL, tRPC | REST-маршруты Hono + Zod | не для этого масштаба |
| Keycloak, Auth0, отдельный сервис входа | вход в самом API | общий вход для нескольких продуктов |
| MongoDB рядом с Postgres | колонка `jsonb` в Postgres | не для этого масштаба |
| Event sourcing, CQRS, саги | статус в колонке и журнал изменений | не для этого масштаба |
| Serverless, облачные функции | обычный процесс в контейнере | не для этого масштаба |
| Реплики, шардинг | один Postgres и ежедневный бэкап | база не тянет после индексов и разбора медленных запросов |
| Nx, Turborepo, общий пакет `shared` | папки в одном репозитории | не для этого масштаба |

Маленький продукт — это меньше серверов и слоёв, а не упрощённая безопасность. Права, вход, деньги, миграции, бэкапы и обработку ошибок делай по-взрослому при любом размере: утечка клиентской базы из CRM на восемь человек — такая же утечка.

## 3. Архитектура: бэкенд, фронт, база

У проекта три части с чёткими границами:

```
браузер  ──►  site   публичный сайт, SSR      ─┐
браузер  ──►  admin  админка или CRM, SPA      ─┼──►  api  ──►  Postgres
Telegram ──►  вебхук бота                      ─┘      │
                                                       └──►  S3 (файлы)
```

- **База** — Postgres. В неё ходит только `api`: он держит схему и миграции.
- **Бэкенд** — `api`. Вся логика, права, расчёты, работа с базой и внешними сервисами.
- **Фронт** — `admin` и `site`. Только показывают данные и отправляют действия в `api`. Решений, от которых зависят данные и деньги, на фронте нет.

| Продукт | Из чего состоит |
|---|---|
| CRM, ERP, учёт, склад для своей команды | `api` + `admin` (SPA) + Postgres |
| Сайт с заявками или блогом | `site` (SSR) + `api` + `admin` (SPA) + Postgres |
| Кабинет клиента с оплатой | `api` + `app` (SPA) + Postgres, лендинг `site` (SSR) — если нужен |
| Telegram-бот с админкой | `api` + `admin` (SPA) + Postgres; бот — вебхуком внутри `api` |

**Сайт — SSR, всё за логином — SPA**
- Публичный сайт — то, что ищут в поиске и чем делятся ссылкой: лендинг, блог, каталог, страницы услуг. Nuxt с SSR на основном домене `example.ru`. SPA поисковик видит пустой страницей, а мессенджеры не собирают для неё превью ссылки.
- Админка, CRM, кабинет — всё, что за логином, — Nuxt SPA (`ssr: false`) на поддомене: `admin.example.ru`, `app.example.ru`.
- API — `api.example.ru`.
- Сайт и админка — разные приложения. У них разные рендер, кэш и заголовки безопасности, и упавшая админка не роняет сайт.
- Сайт нужен, только если есть публичные страницы для поиска. Нет — папки `site/` в проекте нет.

**Когда нужен отдельный сервис**
- Только если у него другое место запуска или другая сеть:
  - тяжёлый рантайм со своим лимитом памяти (Chrome, ffmpeg);
  - шлюз, который должен стоять в другой стране или сети;
  - бот на long-polling, если вебхук невозможен: Telegram пускает к токену только один процесс. Бот на вебхуке живёт внутри `api` и отдельного сервиса не требует.
- **Не дели сервисы по предметным областям** («платежи», «чат», «уведомления») при общей базе. Получится распределённый монолит: копия схемы в каждом сервисе, файлы-близнецы, которые расходятся, межсервисные токены ради одного SELECT, дубли уведомлений при деплое. Так уже было: чат вынесли в отдельный сервис ради WebSocket, а потом влили обратно.
- **У базы один владелец** — `api`. Другие сервисы в неё не ходят. Если без этого никак (сайт читает статьи напрямую ради скорости): только чтение, отдельный пользователь базы с правами на нужные таблицы, поля перечислены в `api/AGENTS.md` с пометкой «менять только вместе с сайтом».
- Если сервисов несколько, у каждой пары свой токен. Пустой токен — «отказ всем», а не «пускать всех».

## 4. Стек по умолчанию

Один язык везде — TypeScript. Каждая часть — популярная и скучная: ИИ знает её хорошо и не выдумывает.

- **Бэкенд:** Node 24, TypeScript `strict` (ESM), Hono 4 + `@hono/node-server`, Zod + `@hono/zod-validator`, Prisma 6 + PostgreSQL 17. Пароли — `bcryptjs`, сессии — `jsonwebtoken`, прокси и таймауты — `undici`, картинки — `sharp`, файлы — S3-совместимое хранилище.
- **Prisma — только шестая, с номером версии:** `pnpm add prisma@6 @prisma/client@6`. Без номера поставится не то: метка `latest` в npm стоит на тестовой восьмой. Седьмая устроена иначе — адрес базы в `prisma.config.ts`, `.env` она сама не читает, — и эти правила, Dockerfile и хук написаны под шестую. Переход на седьмую — отдельная задача с согласия владельца.
- **Фронт:** Nuxt 4 (код в `app/`), Vue 3, Nuxt UI 4 + Tailwind 4, иконки lucide в бандле.
- **Пакеты:** pnpm, lockfile в git, в Docker — `pnpm install --frozen-lockfile`. Один менеджер пакетов на весь проект. Версии моложе суток pnpm не ставит (`minimumReleaseAge` в `pnpm-workspace.yaml`): заражённые выпуски обычно ловят и снимают в первые часы. Эту настройку не убирай. Обновления зависимостей — по желанию через Dependabot или Renovate.
- **Деплой:** Docker и Dokploy на своём VPS.
- **Telegram-боты:** grammy.
- **Очереди и расписания:** таблицы в Postgres.
- **Тесты:** `node:test` через tsx — на деньги, права, вебхуки и разбор внешних ответов.
- Новая зависимость — только с объяснением, зачем. Ради одной функции библиотеку не тащи.
- Версию закрепляй точно, если бинарь должен совпасть: Prisma CLI с клиентом.

## 5. Код: общие правила

Код пишут сессии ИИ одна за другой, и каждая видит только кусок. Поэтому раскладка должна быть предсказуемой: по папке сразу ясно, что в файле можно и чего нельзя. Раскладка каждого сервиса — в его AGENTS.md.

- **Размер.** Файл — до 300 строк, 600 — потолок: такой файл режь. Функция — до 50 строк.
- **Как резать.** По смыслу: по сущности или шагу (`deals/create.ts`, `deals/close.ts`), по куску экрана (`DealHistory.vue`). Не `part2.ts` и не `utils2.ts`.
- **Одна ответственность.** Один файл — одна задача, имя говорит, что внутри: `deals.service.ts`, `DealCard.vue`, `useDeals.ts`.
- **Один источник.** Справочники (статусы, их подписи и цвета, форматы денег и дат) — сразу в одном месте. Логику обобщай на третьей копии, не раньше: неудачная общая функция хуже двух похожих.
- **Типы.** TypeScript `strict`. `any` — только с комментарием, почему иначе нельзя. Ошибку обрабатывай или пробрасывай, пустой `catch` не пиши.
- **Чистота.** Закомментированный код, отладочные `console.log`, неиспользуемые файлы и функции удаляй: история есть в git.
- **Комментарии** объясняют ЗАЧЕМ, а не что. У опасного места пиши, что здесь НЕЛЬЗЯ и почему, с датой случая. Иначе следующая сессия «оптимизирует» обратно.
- **Сторож.** В каждом сервисе есть `scripts/check-architecture.mjs` — скрипт, который читает код и проверяет раскладку и размеры. Что именно он проверяет — в AGENTS.md сервиса. Запускается в `pnpm check`, git-хуком перед каждым коммитом и в GitHub Actions на каждый пуш (`.github/workflows/check.yml`). Нарушение — чини код, а не сторожа.

## 6. База и миграции

- Схему меняет только одна последовательность: правка `schema.prisma` → `npx prisma migrate dev --name <что_меняем>`. На проде миграции применяет контейнер при старте (`prisma migrate deploy`).
- **Запрещено ассистенту:**
  - `db push`, `migrate reset`, `migrate diff`;
  - флаги `--shadow-database-url`, `--accept-data-loss`, `--force-reset`, `--create-only`;
  - `shadowDatabaseUrl` и `directUrl` в схеме, которые смотрят не в локальную базу;
  - ручной SQL: `psql`, `$executeRaw`, `$queryRawUnsafe`;
  - правка файлов в `prisma/migrations/`;
  - SSH-туннель к боевой базе: на `localhost` она остаётся боевой.

  Однажды `migrate diff --shadow-database-url <боевая база>` стёр все таблицы прода: shadow-база для Prisma означает «эту можно затирать».
- Prisma заговорила про `reset`, `drift` или «все данные будут потеряны» — остановись и спроси владельца.
- Схема Prisma чего-то не умеет (частичный индекс, триггер, расширение) — это ручная миграция. Её делает владелец по порядку из `api/prisma/AGENTS.md`, ассистент готовит SQL и объяснение.
- **Разработка — в локальной базе.** Боевая база живёт в Dokploy. Для разработки на компьютере своя: `docker compose up -d db` (файл `docker-compose.yml` в корне). В неё можно мигрировать и сорить тестовыми данными. Боевую ассистент смотрит только на чтение и только через MCP к базе: в режиме `--access-mode restricted` или под пользователем базы с правом SELECT. `psql` к боевой базе хук не пустит.
- **Бэкап** — каждый день, на хранилище вне сервера, восстановление хотя бы раз проверено. Всё остальное бэкап не заменяет.
- Хук `.claude/hooks/guard-db.mjs` блокирует опасные команды. Он работает только в Claude Code. В Codex и Cursor защиту держат эти правила и права пользователя базы.
- Как проектировать таблицы, связи и индексы — `api/prisma/AGENTS.md`.

## 7. Секреты

- Секреты — только в env приложения в Dokploy. В git лежит `.env.example` без значений. Никогда не клади секрет:
  - в код, CLAUDE.md, AGENTS.md или `.mcp.json`;
  - в `NUXT_PUBLIC_*` или `runtimeConfig.public` — это видит любой посетитель;
  - в логи и в чат с ассистентом.
- `.env` — в `.gitignore` и `.dockerignore`. Git-хук не даст закоммитить `.env`, приватный ключ, адрес базы с паролем, токен бота и ключи OpenAI или AWS. Сработал — убери секрет из файла, а не обходи проверку.
- Засветил ключ (в коммите, на скриншоте, на стриме) — перевыпусти. Удаление из git не помогает: ключ остаётся в истории.
- Ключи сторонних сервисов (OpenAI, платёжки, почта) вызываются только с бэкенда. Ключ во фронте — это ключ, которым пользуется кто угодно за твой счёт.

## 8. Персональные данные и закон

Продукт хранит имена, телефоны, почту или документы людей — на него действует 152-ФЗ «О персональных данных». Это не юридическая консультация: продукт с данными клиентов покажи юристу. Но вот что закладывается в код и сервер с первого дня:

- **Хранение в России.** Персональные данные граждан России записываются и хранятся в базе на территории России. Значит, VPS с базой и хранилище бэкапов — в российском дата-центре.
- **Уведомление.** До начала обработки владелец подаёт уведомление в Роскомнадзор (pd.rkn.gov.ru). Это делает человек, не код, — но напомни.
- **Согласие и политика.** На каждой форме, где человек оставляет данные, — галочка согласия на обработку (не стоящая заранее) и ссылка на политику обработки персональных данных. Согласие — отдельным документом, а не пунктом внутри оферты. Политика опубликована на сайте. Факт согласия (кто, когда, на какой текст) пишется в базу.
- **За границу — только осознанно.** Передать данные зарубежному сервису (ИИ вроде OpenAI, зарубежная почта или аналитика) — это трансграничная передача: для неё нужно отдельное уведомление Роскомнадзора. Проще не передавать: перед отправкой в зарубежный ИИ убирай имена, телефоны и документы.
- **Утечка.** Владелец сообщает в Роскомнадзор в течение суток, результаты расследования — в течение трёх суток. Штрафы за утечки большие, за повторную — от оборота. Поэтому храни только нужное, доступ — по правам, в логах персональных данных нет.

## 9. Деплой: Dokploy на одном сервере

Весь продукт живёт на одном VPS с Dokploy: приложения, база, домены, HTTPS, бэкапы. Dokploy — это Docker Swarm и Traefik с понятной панелью:
- пуш в `main` → он сам собирает образ по Dockerfile и выкладывает новую версию;
- сам выпускает и продлевает сертификаты Let's Encrypt;
- поднимает Postgres и делает его бэкапы в S3;
- показывает логи, env и ресурсы каждого приложения.

Для этого масштаба это всё, что дал бы Kubernetes, но без Kubernetes.

- **Не пиши:** манифесты Kubernetes, Helm-чарты, Terraform, GitHub Actions для сборки и выкладки, деплой скриптом по SSH, docker-compose руками на сервере. Проверки (сторожа, тесты) в GitHub Actions можно, выкладка — дело Dokploy.
- **Репозиторий:** один на продукт, в нём папка на каждый сервис (`api/`, `admin/`, `site/`) со своим Dockerfile. В Dokploy у каждой папки своё приложение: Build Path — путь к папке, Watch Paths — чтобы пуш в `admin/` не пересобирал API.
- **Сервер:** с персональными данными граждан России — в российском дата-центре («Персональные данные»).
- **База:** сервис Postgres в том же Dokploy. Приложения ходят к ней по внутреннему имени (`<appName>:5432`), External Port пустой.
- **Домен:** A-запись на сервер → домен у приложения в Dokploy с HTTPS.
- **Секреты и адреса** — в env приложения в Dokploy. Nuxt читает `NUXT_PUBLIC_API_BASE` при старте контейнера: пересобирать ради смены адреса не нужно.
- **Dockerfile:** два этапа; в финальном образе нет исходников и dev-зависимостей; `USER node`; `pnpm install --frozen-lockfile`; `.dockerignore`; `HEALTHCHECK`. Готовые лежат в папке каждого сервиса. Они собираются, когда рядом есть `package.json` и `pnpm-lock.yaml`: создай проект в папке сервиса, lockfile появится после первого `pnpm install`.
- **Проверка здоровья.** `HEALTHCHECK` в Dockerfile ходит в `/health`, а тот — в базу (`SELECT 1`). По нему Swarm понимает, что новая версия поднялась, прежде чем гасить старую.
- **Остановка.** При выкладке старому контейнеру приходит SIGTERM, а через 10 секунд — SIGKILL. Плавная остановка укладывается в 8 секунд или в срок, выставленный в Dokploy (Stop Grace Period в настройках Swarm приложения). Процесс node получает SIGTERM, только если запущен напрямую или через `exec`: оболочка `sh -c` сигнал не передаёт.
- При выкладке старый и новый контейнер какое-то время живут вместе: поэтому фоновые задачи выполняет один ведущий (`api/AGENTS.md`).
- **Порядок выкладки:** если добавились поля, сначала API, потом фронты.
- **Откат:** `git revert` плохого коммита и пуш — Dokploy соберёт прошлую версию. Миграцию revert не откатывает, и это безопасно: миграции только добавляют, и старый код работает с новой схемой.
- Лимит памяти и CPU у каждого приложения — по `memory.peak` под нагрузкой.
- **Тестовый стенд**, если нужен, — второе приложение в том же Dokploy с веткой `dev` и своей базой. Для внутреннего продукта на несколько человек часто не нужен.
- Сервер с нуля, его защита, бэкапы, наблюдение и проверки перед запуском — `docs/server.md`.

## 10. Сеть из России

Для сервера или разработчика в России:
- Пакеты — с зеркала npmmirror через `.npmrc`. `npm -g` `.npmrc` не читает, ему реестр передаётся флагом. Движки Prisma — через `PRISMA_ENGINES_MIRROR`. Готовые настройки — в папках сервисов.
- Сборка и рантайм не ходят в интернет за шрифтами и иконками: всё лежит в бандле.
- Заблокированное (Telegram, OpenAI, Google) — через свой прокси за границей: только CONNECT, логин, белый список хостов. Через прокси идёт только заблокированное, остальное напрямую.
- В Node прокси подключается через `undici` `ProxyAgent` и `dispatcher`. Но grammy ходит через node-fetch и `dispatcher` молча игнорирует, ему нужен `agent`. По логу проверяй, что прокси реально применился.
- Российские банки переходят на сертификаты НУЦ Минцифры. Добавь корневой сертификат в образ (`NODE_EXTRA_CA_CERTS`) и проверь TLS из контейнера.
- У контейнеров IPv4, а некоторые хосты отвечают с сервера только по IPv6. Проверяй `curl -4`, `curl -6` и `fetch` из самого контейнера.

## 11. CLAUDE.md проекта и обновление правил

- В корне — `CLAUDE.md`: что за продукт, масштаб, сервисы и их адреса. В папке сервиса — его `AGENTS.md`: сверху общие принципы, ниже черты `---` — своё для этого проекта.
- Своё растёт по ходу работы. Пустые разделы не держи, заводи раздел с первой записью:
  - **«Правила»** — то, чего не видно из кода: одна фраза + почему + путь к файлу;
  - **«Подводные камни»** — сломалось и починили: дата, что случилось, какое правило выросло;
  - **«Отказались»** — владелец отказался от идеи: что, почему, дата. Иначе следующая сессия предложит её снова;
  - **«Что осталось»** — хвосты по группам: «руками владельцу», «ждёт приёмки», «доделать в коде», «убрать потом» (с условием).
- Задачи — в одном месте (доска или issues), а не россыпью TODO по коду.
- Нет CLAUDE.md в корне — сначала создай его: масштаб и сервисы. Потом код.
- **Обновление правил.** Версия — в начале этого файла, список изменений — `CHANGELOG.md` в репозитории правил. Владелец попросил обновить: сравни версии; общую часть этого файла и файлов сервисов (выше черты `---`), хук, git-хук и сторожей замени новыми; своё ниже черты и CLAUDE.md в корне не трогай.
