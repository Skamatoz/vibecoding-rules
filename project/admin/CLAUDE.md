# Админка — как устроена и по каким принципам строится

Всё, что за логином: админка, CRM, кабинет клиента. Nuxt 4 в режиме SPA (`ssr: false`), Nuxt UI 4, Tailwind 4, иконки lucide в бандле. Данные берёт только из своего API.

Здесь — как строить этот сервис. Общее для проекта — `AGENTS.md` в корне.

## Почему SPA

За логином поисковики не нужны. Без SSR код выполняется только в браузере: нет расхождений между сервером и браузером и не нужно думать, где что запускается. Публичный сайт — отдельное приложение на SSR (`site/`), с админкой его не смешиваем.

## Раскладка

```
app/
  pages/          экраны; тонкие
  components/     по папке на раздел: deals/DealCard.vue, deals/DealForm.vue
    common/       общие кирпичи: поле телефона, пустое состояние, кнопка с подтверждением
  composables/    useApi и по composable на раздел: useDeals, useClients
  middleware/     auth.global.ts — вход, permissions.global.ts — права по адресу
  plugins/        то, что запускается один раз при старте приложения
  layouts/        каркас: меню, шапка
  utils/          чистые функции: деньги, даты, подписи и цвета статусов
nuxt.config.ts    ssr: false, runtimeConfig.public.apiBase
scripts/
  check-architecture.mjs   сторож раскладки и размеров
```

## Кто что делает

Данные идут в одну сторону: **API → `useApi` → composable → страница → компоненты.**

**Страница** собирает экран: берёт данные из composable, раскладывает компоненты, держит фильтры и открытую карточку в query адреса (`?status=new&id=42`) — тогда ссылкой можно поделиться, а кнопка «назад» работает. В странице нет `$fetch`, расчётов и разметки больших форм.

**Компонент** — одна вещь на экране: карточка, форма, таблица, вкладка. Данные получает через props, наверх сообщает через emit. В API сам не ходит.

**Composable** — запросы и состояние раздела. `useDeals` знает список, фильтры, создание и закрытие сделки. Типы ответов API раздела — тоже здесь (`useDeals.ts` экспортирует `Deal`). В API ходят только composables и только через `useApi`.

**`useApi`** — одна обёртка на все запросы:
- адрес из `runtimeConfig.public.apiBase`;
- `credentials: 'include'`;
- разбор ошибки `{ error: { code, message } }`;
- 401 → выход и перезагрузка, 403 — «нет прав», а не выход.

**Middleware** — проверки перед открытием страницы:
- `auth.global.ts` — не вошёл → на страницу входа;
- `permissions.global.ts` — нет права на раздел → «нет доступа». Страницы без пункта меню открываются по прямой ссылке, поэтому права проверяются здесь, а не только в меню.

**Plugins** — то, что запускается один раз при старте: восстановление сессии, общий обработчик ошибок, подключение аналитики. Логики разделов в плагинах нет.

**Layouts** — каркас: меню, шапка. Меню строится из реестра разделов (тот же, что в API), видимость пунктов — по правам.

**Utils** — чистые функции без Vue и запросов. Подписи статусов, цвета, форматы денег и дат живут здесь в одном экземпляре: подпись, поправленная в одном месте из четырёх, однажды разошлась с остальными.

**Состояние.** Отдельный стор (Pinia) не нужен, пока хватает composable с `useState`. Глобально живут только пользователь и его права.

## Размеры

- Страница — до 200 строк, компонент — до 300. 600 — потолок.
- Большая карточка — вкладки отдельными компонентами. Большая форма — компонент формы плюс composable с отправкой.
- Одинаковый кусок интерфейса в третьем месте — общий компонент в `components/common/`.

## Сторож

`scripts/check-architecture.mjs` — скрипт, который читает `app/` и проверяет:
- в страницах, компонентах и layouts нет `$fetch` и `useFetch` — в API ходят composables;
- в `utils/` нет запросов и composables;
- нет файлов длиннее 600 строк. Страница длиннее 200 строк и компонент длиннее 300 — предупреждение.

Подключение — в `package.json`:

```json
"scripts": {
  "check:arch": "node scripts/check-architecture.mjs",
  "check": "pnpm build && pnpm check:arch"
}
```

`pnpm check` — перед каждым коммитом. Нашёл нарушение — чиним код, сторожа не ослабляем.

## Фронт не решает

- Суммы, периоды, пороги и «можно ли нажать» приходят от API готовыми полями (`canPay: true`). Фронт не повторяет бизнес-правила: кнопка «Выплатить» активна по тому же полю, по которому сервер разрешит операцию.
- Спрятать кнопку без права — удобство, а не защита. Защищает сервер.

## Интерфейс

- У каждого списка и карточки три состояния: загрузка, пусто, ошибка. Белый экран — не состояние.
- Ошибку показывай текстом сервера. Ошибку загрузки не глуши `console.error`: человек должен видеть, что данные не пришли.
- Незнакомое значение с сервера показывай его ключом, а не прячь.
- Разрушающее действие — через модалку подтверждения. Изменение, которое уходит во внешнюю систему, — через модалку «было → станет».
- Кнопка во время отправки заблокирована: двойной клик не создаёт две записи.
- Длинный текст: явная кнопка «Сохранить», Cmd/Ctrl+S, предупреждение при уходе со страницы. Сохранения идут одной очередью, чтобы ответ на старый запрос не перебил свежую правку.
- Состояние, которое видит человек (прочитано, колонки таблицы, вид), хранится на сервере у учётки, а не в localStorage. Иначе на другом устройстве всё сбросится.
- Ширина 390 px проверена. Отступы задаёт страница, а не компонент.
- `:hover` — только внутри `@media (hover: hover)`: на телефоне залипшее наведение мешает нажатиям.
- Цвета — токены темы, а не случайные hex в компонентах.
- Tailwind-классы — литеральными строками, не склейкой: сканер вырежет склеенное.

## Безопасность

- В `runtimeConfig.public` и `NUXT_PUBLIC_*` — только то, что можно показать любому: адрес API — да, ключи — никогда.
- `v-html` с пользовательскими данными нельзя. Markdown — с `html: false`.
- Админку нельзя открывать во фрейме: `X-Frame-Options: DENY` и `frame-ancestors 'none'` в `routeRules`.
- Source map в прод не выкладывай.
- PWA, если нужна: `registerType: 'prompt'`; кэшируется только оболочка, ответы API — нет: данные устаревают, а персональные данные оседают в Cache Storage. После сборки проверь, что `sw.js` на месте.
